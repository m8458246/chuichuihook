# 定位伪造：坐标系、漂移与字段覆盖

> 本篇讲定位类模块最容易踩、也最容易被误判的一块：**坐标系**。
> 03 第 8 条讲的是"改了坐标地址不变"（两个字段独立），本篇讲的是"坐标对了但落点偏 300 米"（坐标系错配）。

## 1. 三层坐标系，混用就偏

| 坐标系 | 谁在用 | 和 WGS84 的差 |
|---|---|---|
| **WGS84** | GPS 原始值、`LocationManager`、OpenStreetMap、境外地图 | 基准 |
| **GCJ-02**（火星坐标） | 高德、腾讯、Google 中国、绝大多数国产 App | 300~600 米 |
| **BD-09** | 百度地图 / 百度定位 SDK | 在 GCJ-02 上再偏一次 |

**关键事实**：Android 的 `LocationManager` 返回的一定是 **WGS84**，系统不会帮你转。
高德/百度 SDK 返回的一定是 **GCJ-02 / BD-09**。

**所以**：用 `LocationManager` 采集坐标，再喂给高德系 SDK，就会偏。

## 2. 实测：362 米

本项目真实数据（昆明）：

```
LocationManager 返回（WGS84）：  25.067920, 102.700413
dumpsys location 原始值：         25.07****, 102.70****   ← 同一个
WGS84 → GCJ-02 转换后：          25.064933, 102.701831
偏移：362 米
```

现象：**真实位置能打卡，采集后存进去的坐标不能打卡**。
原因就是 362 米，刚好超出打卡半径。

**排查顺序**（别再怀疑 hook）：

1. `dumpsys location | grep "last location"` 拿系统原始值（脱敏显示，但能对上前几位）
2. 和配置里存的坐标对比，如果一致 → 说明存的就是 WGS84
3. 用转换算法算一下 GCJ-02，看偏移多少
4. 偏移 300~600 米 → 100% 是坐标系问题，不是 hook 问题

## 3. 转换代码（可直接用）

```java
public final class CoordConverter {
    private static final double A = 6378245.0;
    private static final double EE = 0.00669342162296594323;

    public static boolean outOfChina(double lat, double lng) {
        return lng < 72.004 || lng > 137.8347 || lat < 0.8293 || lat > 55.8271;
    }

    /** WGS84 → GCJ-02 */
    public static double[] wgs84ToGcj02(double lat, double lng) {
        if (outOfChina(lat, lng)) return new double[]{lat, lng};
        double dLat = transformLat(lng - 105.0, lat - 35.0);
        double dLng = transformLng(lng - 105.0, lat - 35.0);
        double radLat = lat / 180.0 * Math.PI;
        double magic = Math.sin(radLat);
        magic = 1 - EE * magic * magic;
        double sqrtMagic = Math.sqrt(magic);
        dLat = (dLat * 180.0) / ((A * (1 - EE)) / (magic * sqrtMagic) * Math.PI);
        dLng = (dLng * 180.0) / (A / sqrtMagic * Math.cos(radLat) * Math.PI);
        return new double[]{lat + dLat, lng + dLng};
    }

    /** GCJ-02 → WGS84（迭代反解，误差 < 1 米） */
    public static double[] gcj02ToWgs84(double lat, double lng) {
        if (outOfChina(lat, lng)) return new double[]{lat, lng};
        double wgsLat = lat, wgsLng = lng;
        for (int i = 0; i < 3; i++) {
            double[] gcj = wgs84ToGcj02(wgsLat, wgsLng);
            wgsLat += lat - gcj[0];
            wgsLng += lng - gcj[1];
        }
        return new double[]{wgsLat, wgsLng};
    }
}
```

**采集流程的正确顺序**：

```
LocationManager 拿到 WGS84
   ├─ 转 GCJ-02 → 填进坐标输入框（存这个）
   └─ 原始 WGS84 → 送 Geocoder 逆地理编码（这样地址才准）
```

**为什么逆地理编码要用 WGS84**：Android 的 `Geocoder` 在国内（尤其是 Google 实现）期望 WGS84 输入；
用转换后的 GCJ-02 去查，地址会偏移到隔壁街区。

**手动填坐标**不要转换 —— 从高德/腾讯地图复制来的已经是 GCJ-02。

## 4. 漂移：圆盘内均匀采样

要求：每次定位坐标不能一样，但同一次定位读多次不能抖。

```java
public static double[] offset(double lat, double radius) {
    if (radius <= 0) return new double[]{0, 0};
    double r = radius * Math.sqrt(Math.random());   // ← 关键：sqrt 保证圆盘内均匀
    double theta = Math.random() * Math.PI * 2;
    double dLat = (r * Math.cos(theta)) / 111320.0;
    double cos = Math.cos(Math.toRadians(lat));
    if (Math.abs(cos) < 1e-6) cos = 1e-6;
    double dLng = (r * Math.sin(theta)) / (111320.0 * cos);
    return new double[]{dLat, dLng};
}
```

**为什么用 `sqrt(random)`**：如果直接 `r = radius * random`，点会聚集在圆心；
乘 `sqrt` 之后才是圆盘内均匀分布。

**经验值**：5 米对打卡场景够用；太小（1~2 米）看起来像没动，太大（50 米+）可能超出范围。
半径做成可配置，默认 5。

**同一次定位内不抖**：把偏移按"定位对象实例"缓存，或干脆每次回调重新算一次
（本项目选后者，因为钉钉每次回调都是新对象，重新算反而更自然）。

## 5. 字段覆盖：遍历 setter 而不是硬编码

原版锤锤硬编码了 27 个 `setXxx`。本项目改成**遍历真实对象的全部 setter**：

```java
static int copyFields(Object src, Object dst) {
    int n = 0;
    for (Method setter : dst.getClass().getMethods()) {
        String name = setter.getName();
        if (!name.startsWith("set") || setter.getParameterCount() != 1) continue;
        String suffix = name.substring(3);
        Object value;
        try {
            Method getter = src.getClass().getMethod("get" + suffix);
            if (getter.getReturnType() != setter.getParameterTypes()[0]) continue;
            value = getter.invoke(src);
        } catch (Throwable e) { continue; }
        try { setter.invoke(dst, value); n++; } catch (Throwable ignored) {}
    }
    return n;
}
```

**实测覆盖 43 个字段**（比硬编码多 16 个），高德以后加字段也能自动覆盖。

**注意**：`null` 值也要覆盖。`extras`、`locationDetail` 这类对象字段如果跳过 null，
真实位置的详细信息会残留，等于没伪造干净。

## 6. 日志审计：证明 hook 真的生效

日志每行格式（最新在上）：

```
11-11 20:25:12  25.067907,102.700384  目标 25.067920,102.700413  偏移 3.3m  字段 43  云南省昆明市五华区…
```

四个关键信息：

| 字段 | 能证明什么 |
|---|---|
| 实际坐标 | 钉钉最终拿到的值 |
| 目标坐标 | 配置里的基准点 |
| 偏移 | 漂移在生效，且在半径内 |
| 字段数 | 覆盖了多少个 `setXxx`（43 = 全量） |

**如果一行都没有** → 模块没加载，或者钉钉没触发定位。
**如果字段数 < 40** → 高德 SDK 版本变了，`setXxx` 有增删，不影响使用但要留意。
**如果偏移恒为 0** → 半径配成 0 了。

**写入方式**：Android 11+ 不能直接 `File` 写 `/sdcard`，走 MediaStore：

```java
ContentValues cv = new ContentValues();
cv.put(MediaStore.Downloads.DISPLAY_NAME, "hook.log");
cv.put(MediaStore.Downloads.MIME_TYPE, "application/octet-stream"); // ← 别用 text/plain
cv.put(MediaStore.Downloads.RELATIVE_PATH, "Download/chuichuihook/");
Uri uri = resolver.insert(MediaStore.Downloads.EXTERNAL_CONTENT_URI, cv);
```

**两个坑**（03 第 6 条只提了同名改名，这里补充）：

1. `MIME_TYPE = "text/plain"` 会让 MediaStore **自动补 `.txt` 后缀**，
   于是 `DISPLAY_NAME = "hook.log"` 的精确查询永远匹配不到，每次都 insert 新文件（本项目一度攒了 20 个）。
   → 改用 `application/octet-stream`，或者查询用 `DISPLAY_NAME LIKE 'hook.log%'`。
2. 覆盖写要用 `openOutputStream(uri, "wt")`（truncate 模式），普通 `"w"` 不会截断。

## 7. 三个常见误判

| 现象 | 不是这个原因 | 真正原因 |
|---|---|---|
| 坐标改了但页面地址没变 | hook 没生效 | 地址和坐标是两个独立字段（03 第 8 条） |
| 采集的位置不能打卡 | 定位精度不够 | 坐标系错配，偏 300~600 米 |
| 日志偏移每次都在 0.1m 内 | 漂移没生效 | 半径配太小，或者用了 `random` 而不是 `sqrt(random)` |
