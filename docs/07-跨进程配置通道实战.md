# 跨进程配置通道实战（锤锤102 项目补充）

> 本篇是 `03-踩坑与解决.md` 第 1、2 条的**补充和修正**，另外补上当时没深挖的部分。
> 01-06 讲的是 ejiahook（百度定位、Cordova 混合应用）的经验；本篇来自 chuichui（高德定位、钉钉）
> 这个项目，场景不同，结论有修正。

## 一句话结论

**模块 App 和目标进程之间传配置，只有两条路真正可靠：**

1. `openRemoteFile()`（LSPosed 的共享数据目录，需要 root 写）
2. **让目标进程自己存**（写目标 App 的 SharedPreferences）

`ContentResolver.call`、`getRemotePreferences`、普通广播在**目标 App targetSdk ≥ 30** 时全部会失效，
原因不是权限没配好，是 **Android 11+ 包可见性**。

---

## 1. 四条通道的失效矩阵

目标：钉钉 `com.alibaba.android.rimet`，`targetSdk=30`；模块 `com.cycy.chuichui`，`targetSdk=34`。

| 通道 | 结果 | 真实原因 |
|---|---|---|
| `ContentResolver.call(provider)` | ❌ `IllegalArgumentException: Unknown authority` | 包可见性：钉钉看不到模块包 |
| `sendBroadcast(setPackage)` | ❌ 广播被 AMS 静默丢弃，`resultCode` 停在初值 | 同上 |
| `sendBroadcast(ComponentName)` | ⚠️ 模块 App 未被 force-stop 时可用 | 显式组件仍受**调用方**可见性约束 |
| `getRemotePreferences(group)` | ⚠️ 永远返回空 map | 见第 3 节：daemon 读的是 SQLite，模块侧没有写入口 |
| **`openRemoteFile(name)`** | ✅ 稳定 | daemon 通过 Binder 传 fd，不经过包可见性 |
| **目标 App 自己的 prefs** | ✅ 最稳 | 模块代码就在目标进程里，写自己的文件合法 |

### 对 03 第 1 条的修正

03 里把 `Unknown authority` 归因为「ColorOS 的冻结 / 系统对跨应用 Provider 的额外限制」，
**实际是 Android 11+ 的包可见性**：

- 钉钉 `targetSdk=30`，受包可见性限制
- 模块 App 没被钉钉的 `<queries>` 声明 → 钉钉解析不到 `com.cycy.chuichui.config`
- 用 `content call` 从 shell 测试是**通的**（shell 有 `QUERY_ALL_PACKAGES`），所以容易误判成"Provider 没写对"

**验证方法**：在目标进程里打印异常类型。`Unknown authority` = 解析不到 provider（可见性），
`SecurityException: Permission Denial` = 权限问题，两者要分开。

## 2. 包可见性的完整影响面

`targetSdk ≥ 30` 的 App，以下操作都会被过滤：

| 操作 | 受影响 |
|---|---|
| `getPackageInfo` / `queryIntentActivities` | ✅ 受影响 |
| `ContentResolver.call` / `query` | ✅ 受影响 |
| `sendBroadcast`（隐式） | ✅ 受影响 |
| `sendBroadcast`（`setPackage`） | ✅ 受影响 |
| `sendBroadcast`（`ComponentName`） | ✅ **也受影响**（调用方不可见就丢弃） |
| `startService` / `bindService` | ✅ 受影响 |
| `openRemoteFile`（LSPosed 通道） | ❌ 不受影响（走 Binder 传 fd） |
| 目标 App 自己的 SharedPreferences | ❌ 不受影响（同进程） |

**唯一绕过办法**：让目标 App 的 `<queries>` 声明你的包 —— 改不了别人的 APK，所以等于无解。

**结论**：不要把「拉取配置」设计成「目标进程主动去问模块 App」，
除非你能保证目标 App 的 targetSdk < 30。

## 3. `getRemotePreferences` 为什么永远空

反编译 `daemon.apk` 的 `classes.dex` 可以确认（方法名混淆成 `j7.r()` / `j7.v()`）：

```java
// daemon 侧，读取 prefs 的实际实现
public final HashMap v(int userId, String pkg, String group) {
    return this.w.computeIfAbsent(new Pair(pkg, userId), new w6(this))
            .getOrDefault(group, new HashMap());
}

// w6.apply -> j7.r(pkg, userId)
public final ConcurrentHashMap r(String pkg, int userId) {
    Cursor c = this.f94a.query(...);   // ← f94a 是 SQLiteDatabase
    ...
}
```

**关键点**：LSPosed 2.2.1 的 remote prefs 存在 **daemon 的 SQLite 数据库**里，
不是读模块 App 的 `shared_prefs/*.xml`。而 libxposed 的 API **只提供读，没有写**。

所以模块 App 写自己的 `SharedPreferences("profile")`，`getRemotePreferences("profile")` 也拿不到。

> 03 里说"daemon 那边没给出来（可能和模块 App 的 prefs 状态/时序有关），没继续深挖"——
> 现在可以结案了：**不是时序问题，是数据源根本不同**。

## 4. `openRemoteFile` 的真实路径

官方文档只说 "module's shared data directory"，不写具体位置。实际路径：

```
/data/adb/lspd/modules/<userId>/<packageName>/files/
```

例如：

```
/data/adb/lspd/modules/0/com.cycy.chuichui/files/profiles.json
```

**怎么确认的**（这套方法比猜快得多）：

1. `jadx` 反编译 `/data/adb/modules/zygisk_lsposed/daemon.apk` 的 `classes.dex`
2. 搜 `ParcelFileDescriptor`，找到 `onTransact` 的分支 3/4
3. 分支里是 `c6.q(userId, -1, pkg, "<dir>").resolve(name)`，`c6.q` 的实现是
   `b.resolve(String.valueOf(userId)).resolve(pkg).resolve(dir)`
4. `b` 是静态常量，再看它的初始化就拿到根目录

**目录权限**：`/data/adb` 是 `700 root:root`，普通 App **无法遍历**，
所以模块 App 自己写不了，只能：
- 借 `su` 复制（需要 root 授权）
- 或者让用户用 MT 管理器手动复制

**坑**：`openRemoteFile` 的 `name` 参数**不能带路径分隔符**，只能传文件名。

## 5. 广播通道的正确用法

即使用广播，也要满足两个条件：

```java
Intent intent = new Intent("com.cycy.chuichui.GET_CONFIG");
// 1) 显式组件（setPackage 在包可见性下会被丢弃）
intent.setComponent(new ComponentName("com.cycy.chuichui",
        "com.cycy.chuichui.provider.ConfigReceiver"));
// 2) 模块 App 被 force-stop 过（stopped 状态）也要能收到
intent.addFlags(Intent.FLAG_INCLUDE_STOPPED_PACKAGES);
```

接收端必须是**静态注册**的 receiver（`AndroidManifest.xml` 里声明，`exported="true"`），
这样进程被杀也能被拉起。

**实测**：

| 模块 App 状态 | 广播结果 |
|---|---|
| 进程存活 | ✅ 秒回 |
| 进程被杀（`am kill`） | ✅ 能拉起，慢 1~2 秒 |
| force-stop（stopped） | ❌ 丢弃（即使加了 `FLAG_INCLUDE_STOPPED_PACKAGES`，包可见性优先级更高） |

## 6. 最优解：让目标进程自己存

既然模块代码跑在目标进程里，最可靠的做法是**把配置写进目标 App 自己的 SharedPreferences**：

```java
// 目标进程内（hook 侧）
private static SharedPreferences targetPrefs(Context ctx) {
    return ctx.getSharedPreferences("chuichui_config", Context.MODE_PRIVATE);
}

private static void persist(Context ctx, String json) {
    targetPrefs(ctx).edit().putString("profiles", json).commit();
}
```

**优点**：

- 不需要 root、不需要跨进程通道、不受包可见性影响
- 目标 App 重启后照样能读到
- 只要成功过一次（推送/广播/文件任一通道），以后永久可用

**读取顺序**（实际代码）：

```
1. 目标 App 自己的 prefs        ← 第一优先级
2. openRemoteFile（共享目录）   ← 有 root 同步时的兜底
3. getRemotePreferences
4. ContentProvider
5. 显式广播请求
6. 模块 App 主动推送
```

任何一条通道拿到的配置都会**回写进 prefs**，形成自愈。

**坑**：改目标 App 的 prefs **文件**不会立刻生效——
`SharedPreferences` 在进程内是单例缓存，必须 force-stop 目标 App 才会重新读文件。

## 7. 配置热更新

模块 App 保存配置后主动推送，目标进程常驻 receiver 接收：

```java
// 模块 App 侧
Intent i = new Intent("com.cycy.chuichui.PUSH_CONFIG");
i.setPackage("com.alibaba.android.rimet");
i.putExtra("json", json);
i.addFlags(Intent.FLAG_INCLUDE_STOPPED_PACKAGES);
ctx.sendBroadcast(i);

// 目标进程侧（Application.onCreate 时注册）
IntentFilter f = new IntentFilter("com.cycy.chuichui.PUSH_CONFIG");
// Android 13+ 必须显式声明 RECEIVER_EXPORTED(2)，否则收不到跨应用广播
ctx.registerReceiver(receiver, f, Context.RECEIVER_EXPORTED);
```

**注意**：推送的配置要标记 `fromPush` 并给更长的 TTL（本项目 5 分钟），
否则 3 秒后重新 `load()` 会读回共享目录里的旧配置。

## 8. 选型决策树

```
目标 App targetSdk < 30 ?
├─ 是 → Provider / 普通广播都能用，随便选
└─ 否 → 包可见性生效，只能：
        ├─ 模块有 root → openRemoteFile（/data/adb/lspd/modules/<uid>/<pkg>/files/）
        ├─ 目标进程能自己存 → 首选，写目标 App 的 prefs
        └─ 都不行 → 显式广播（依赖模块 App 不被 force-stop）+ 推送兜底
```

**经验**：这类模块的配置通道不要只做一条，做 3~4 条带优先级的回退链，
任何一条成功就回写持久化，这样用户完全不用关心底层走的是哪条。
